Host 已经按这句用户话写过 `working_brief`。先读更新后的 JSON，看实际改了哪几个字段，不要凭对白猜测。

## 先分清改的是哪一类

- 改诉求（主题、目标、观众、时长、平台、体裁）：走本 skill，不要去改镜头。
- 改已经做出来的某一段（「第一段太短」「这句换掉」）：不要在这里修，告诉自己下一拍走 `revise-segment`。
- 两件事缠在一起：只先确认诉求，正文先不动。

对照 `working_intent`。brief 和已经承诺的 intent 打架时，只问用户以谁为准，不要默默覆盖，也不要直接 `start_project` 或 `repair`。

## 已经有项目时怎么问

制作已经跑过，改口通常意味着旧脚本不再匹配。用一句人话点出**变了的那一项**，再问范围：

- 主题/目标变了：整支按新任务书重做，还是只改对不上的那一段。
- 只改时长或平台、主题没变：说清楚这会影响节奏和篇幅，问要不要按新约束重做叙事。

不要自己改正文，不要默默再 `start_project`。用户明确说整支重做，再走 `start-project`（若项目已在跑，先说明不能重复开工，问是否按新 brief 修叙事）。用户明确说只改某一段，下一拍再 `revise-segment`。

## 还没开工时

只确认 Host 写入的新字段够不够具体。太薄就按 `clarify-brief` 的标准只补一项。不要为改口而催开工。

## 输出格式

本拍对用户确认一句，不要直接开工或 repair。

```json
{
  "tool": null,
  "arguments": {},
  "message": "主题改成了端午节科普。按新主题整支重做，还是只改某一段？",
  "done": false
}
```

`message` 要点出变化，不要复述整个 brief。brief 和 intent 打架时，只问以谁为准。
